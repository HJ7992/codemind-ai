# 项目与索引任务状态机

- 状态：已冻结
- 适用范围：MVP 单实例 Spring Boot + 单实例 FastAPI 的本地部署
- 上位规范：[MVP 设计冻结](../mvp-design-freeze.md)

## 1. 基本原则

- MySQL 是项目和任务状态的唯一权威来源。
- 项目状态只允许 `INDEXING`、`READY`、`INDEX_FAILED`、`DELETING`。
- 索引任务状态只允许 `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`。
- 每个任务绑定不可变的 `source_version_id`，每个源码版本至多一个任务。
- 不增加隐式状态。异步删除通过项目 `DELETING` 和持久化错误信息表达，不新增删除任务状态。
- 状态更新使用数据库行锁和条件更新，不能仅依赖内存中的旧状态。
- 所有时间使用 UTC；`attempt_count`、`max_attempts` 和心跳用于恢复，不代表新业务状态。

## 2. 项目状态转换

| 当前状态 | 事件与前置条件 | 下一状态 | 原子结果 | 失败处理与重试 |
|---|---|---|---|---|
| 不存在 | ZIP、隐私确认、安全和 UTF-8 校验全部通过；持久化项目、版本和任务 | `INDEXING` | 活动版本为 NULL；任务为 `PENDING` | 任一写入失败回滚并清理临时文件；客户端不自动重试 POST，用户可重新上传 |
| `INDEXING` | AI 完整索引成功；点数验证通过；项目/任务/版本仍匹配 | `READY` | 同一事务设置任务 `SUCCEEDED`、活动版本和项目状态 | 任一项不满足则禁止 READY；按任务失败规则处理 |
| `INDEXING` | 解析、Embedding、Qdrant、校验失败或恢复次数耗尽 | `INDEX_FAILED` | 任务 `FAILED`，活动版本保持 NULL，保存脱敏错误 | 清理该版本临时向量；MVP 不做原地人工重试，用户重新上传创建新项目/版本 |
| `INDEXING` | 用户删除 | `DELETING` | 先锁定项目并标记删除，阻止 READY 和新问答 | 按第 5 节删除编排；可重入恢复 |
| `READY` | 用户删除 | `DELETING` | 阻止新问答；已有历史在删除完成前可读 | 按第 5 节删除编排 |
| `INDEX_FAILED` | 用户删除 | `DELETING` | 进入清理流程 | 按第 5 节删除编排 |
| `DELETING` | 向量、源码和业务数据全部删除 | 不存在 | GET 项目返回 404 | 任一步失败保持 `DELETING`，记录脱敏阶段错误并安全重试 |

禁止转换：

- `INDEX_FAILED → READY`：没有新的完整成功索引，禁止直接改状态。
- `DELETING → 任意状态`：删除不可撤销。
- `READY → INDEXING`：MVP 没有原地重建接口。
- 未设置匹配的活动版本时进入 `READY`。

## 3. 索引任务状态转换

| 当前状态 | 触发条件 | 下一状态 | 必须满足的结果 |
|---|---|---|---|
| 不存在 | 上传校验和事务成功 | `PENDING` | 绑定项目、版本；`attempt_count=0` |
| `PENDING` | 后台工作者获取任务，项目仍为 `INDEXING` | `RUNNING` | 条件更新成功；尝试次数加 1；写心跳 |
| `RUNNING` | AI 返回成功且完整点数校验通过 | `SUCCEEDED` | 与项目 `READY`、活动版本在同一事务提交 |
| `RUNNING` | 模型、解析、Qdrant、超时或完整性校验失败 | `FAILED` | 项目同时变为 `INDEX_FAILED`；活动版本不变；错误脱敏 |
| `PENDING/RUNNING` | 项目开始删除 | `FAILED` | 错误码 `PROJECT_DELETING`；不得再进入成功转换 |
| `RUNNING` | 服务异常退出 | 重启时按恢复规则处理 | 不直接保留一个永远运行的内存任务 |

`SUCCEEDED` 和 `FAILED` 为正常终态。MVP 不提供 `FAILED → PENDING` 的公开重试；失败项目的重试方式是重新上传，从而得到新的项目、版本和任务 ID。

### 3.1 成功判定

只有同时满足以下条件才能 `RUNNING → SUCCEEDED`：

1. 响应中的 `jobId`、`projectId`、`sourceVersionId` 与任务完全一致。
2. AI 已处理所有应处理源码，返回计数有效。
3. Qdrant 中该双过滤范围内的代码块点数与期望一致。
4. 项目仍为 `INDEXING`，任务仍为 `RUNNING`，项目未进入删除。
5. 数据库事务成功提交。

Embedding 超时、Chat 配置异常（若影响索引配置校验）、部分写入或响应丢失均不能标记成功。

## 4. 重试与幂等

### 4.1 正常运行

- 模型 Chat/Embedding 请求不做应用内自动重试，避免重复计费和难以判定的半成功；超时按失败处理。
- `PENDING` 任务只由一个工作者条件领取。
- `RUNNING` 任务在单实例进程内通过任务 ID 防重；AI 对 `source_version_id` 再加互斥锁。
- AI 索引请求是“针对未活动版本的可重建操作”：重入前清理该版本临时点，用确定性 point ID 重建。活动版本禁止原地重建。
- 网络超时不代表对端没有执行，调用方不得立刻并发发起第二个索引请求。

### 4.2 服务重启恢复

Spring Boot 启动时按数据库状态恢复：

| 发现状态 | 恢复动作 |
|---|---|
| 项目 `INDEXING` + 任务 `PENDING` | 重新领取，遵守最大尝试次数 |
| 项目 `INDEXING` + 任务 `RUNNING` | 等待 AI 版本锁可获取后，以相同任务/版本执行恢复重建；尝试次数加 1；不得创建新版本 |
| 项目 `INDEX_FAILED` + 任务 `FAILED` | 保持失败，不自动产生模型费用；等待用户删除或重新上传 |
| 项目 `READY` + 任务 `SUCCEEDED` | 不重建，不切换版本 |
| 项目 `DELETING` | 从持久化删除阶段检查点继续幂等清理，不恢复索引或问答 |

恢复上限由 `CODEMIND_INDEX_MAX_ATTEMPTS=2` 控制，包含正常执行与崩溃恢复。达到上限仍无法确认成功时，任务和项目分别进入 `FAILED`、`INDEX_FAILED`。每次尝试的语义和计数必须有单元测试，防止重试次数 off-by-one。

AI 重启时：

- 未收到完成响应的索引不能凭内存状态宣称成功。
- 版本级删除墓碑必须持久化并在重启后生效。
- Spring 的恢复请求通过双过滤清理和确定性 ID 重建未活动版本。

## 5. 删除与索引并发

### 5.1 删除顺序

1. 在事务中锁定项目，将状态改为 `DELETING`；新问答、活动版本切换和新索引领取立即被拒绝。
2. 将关联 `PENDING/RUNNING` 任务标记为 `FAILED(PROJECT_DELETING)`，使索引完成方后续无法提交 READY。
3. 等待本进程已发起的 AI 索引调用退出；AI 的版本级互斥锁保证删除不会与写入同时操作同一版本。
4. 调用内部删除接口。AI 获取同一版本锁，删除该版本代码块点并写入持久化删除墓碑。重复删除返回成功。
5. 删除该版本受控源码目录；重复调用时目录不存在也视为成功。
6. 在事务中先将活动版本置空，再按外键顺序删除会话/消息/引用、任务、文件、版本和项目。
7. 全部完成后项目不再可查。墓碑保留，防止迟到请求重建已删除版本。

### 5.2 部分失败

- 任一步失败，项目保持 `DELETING`，记录脱敏的删除阶段和安全错误。
- `GET project` 可返回 `DELETING` 及安全错误摘要；重复 DELETE 继续执行，不报成功完成。
- Qdrant 删除成功、源码删除失败时，重试从源码阶段继续；不得重复声称向量仍存在。
- 业务数据删除失败时，重试向量与源码删除均应幂等。
- 删除过程中项目不能问答；即使临时向量残留，也不会形成“可用但已删除”的公开索引。
- AI 删除墓碑使迟到的同版本索引请求返回 410；项目/版本 ID 永不复用。

## 6. 版本切换与隔离

- 新版本索引期间，`active_source_version_id` 仍指向旧可用版本；若按 MVP 单版本流程没有旧版本，则保持 NULL。
- 只有新版本完整成功后，才允许在事务中更新活动版本。
- 每个问答请求记录并传递本次活动 `source_version_id`，检索同时过滤项目与版本。
- 切换后清理旧版本属于独立删除动作；旧向量即使尚未清理，也不能进入新版本结果。
- MVP 不开放向既有项目添加版本的公开接口；未来增加时不得绕过上述原子切换规则。

## 7. 必须覆盖的状态测试

- 所有合法转换及至少一个非法转换矩阵测试。
- Embedding 超时、部分 Qdrant 写入、计数不一致均不能 READY。
- AI 成功但数据库提交失败后恢复，不产生重复有效点或错误状态。
- 删除与 `PENDING`、`RUNNING`、成功提交临界点并发，最终均不能问答或重新索引。
- 删除在向量、源码、数据库三个阶段分别失败后重试。
- 重启恢复 `PENDING`、`RUNNING`、`DELETING`，验证 `max_attempts=2` 的精确计数。
- 两个项目、两个版本的 Qdrant 双过滤隔离。
- 删除墓碑在 AI 重启后仍拒绝同版本索引。

验收证据要求见[测试验收清单](../testing/mvp-acceptance-checklist.md)。
